# PHASE 1 — 홍보잇다 제품 감사 및 재설계 전략

작성일: 2026-10-09 (한국 시간)
대상: ad_prototype의 React + Vite 애플리케이션
결론: 홍보잇다를 ‘사진과 설명을 홍보물로 바꾸는 우리 가게 작업실’로 재구성한다. 첫 화면에서 입력을 시작하고, 한 작업의 진행과 저장을 끝까지 안내하는 서비스가 목표다.

## 1. 조사 범위와 증거 수준

AGENTS.md와 DESIGN_MASTER.md를 모두 끝까지 읽었다. 이번 사용자 요청의 Phase 1 제한에 따라 애플리케이션 소스·스타일·의존성·실행 설정을 변경하지 않았다. 이 문서만 새로 작성했다.

직접 읽은 주요 구현은 src/App.tsx, src/StudioScreens.tsx, src/index.css, src/studio.css, src/canvasText.ts, src/main.tsx, package.json, vite.config.ts, index.html이다. LOCAL_PREVIEW.md와 기존 검증 스크립트·JSON, 저장된 홈·로그인·결과 캡처를 보조 증거로 사용했다.

시각 검토에 사용한 캡처:
- ui-review/guide-390.png 및 guide-1440.png: 모바일·데스크톱 첫 화면
- ui-review/clean-login-390.png: 현재 로그인 구성
- ui-review/results-390-large.png: 모바일 큰 글씨 결과 화면

캡처와 검증 JSON은 기존 작업의 산출물이며 이번 감사에서 새로 실행한 결과가 아니다. App.tsx는 결과 캡처보다 나중에 수정되어 있어, 캡처와 최신 소스가 완전히 일치한다고 단정하지 않는다.

이번 세션의 실행 도구는 프로세스 생성 오류가 발생했고, 설치된 Playwright 경로는 접근 권한 오류가 발생했다. 브라우저 연결 목록도 비어 있어 현재 앱의 실시간 렌더링·새 빌드·실기기 검증은 수행하지 못했다. 별도 개발 서버를 시작하지 않았다.

외부 레퍼런스는 웹 도구로 공개 페이지 본문에 성공적으로 접근했다. 외부 서비스의 실제 변환·QR 생성·다운로드를 실행하거나 모바일 화면·오류 상태·시각적 색상을 브라우저로 검증한 것은 아니다. 아래 참고사이트의 기능 배치와 안내 구조는 페이지 내용에서 확인한 사실이며, 홍보잇다에 대한 적용안은 본 감사의 설계 판단이다.

과거 UI_NEXT_STEPS.md의 역사 홈페이지 중심 방향보다 최신 사용자 요청과 DESIGN_MASTER.md의 현대 서비스 연구 방향을 우선했다.

## 2. 기존 애플리케이션 분석

### 2.1 제품과 사용자 흐름

브랜드는 ‘홍보잇다’, 대상은 제품 사진으로 가게 홍보물을 만드는 소상공인이다. 현재 페이지 상태는 login / home / create / records / plan이며 URL 라우팅 없이 React 상태로 화면을 전환한다.

현재 주요 경로:
1. 로그인·회원가입 양식 또는 ‘바로 시작하기’ → 홈
2. 홈의 ‘만들러 가기’, 퀵바의 ‘만들기’, 단독 제작 메뉴 → 제작 1단계
3. 제품 사진 1장 선택 → 종류·홍보할 곳 선택 → 2단계
4. 제품 설명·강조할 특징·주요 고객 수정 → 선택 검색어(#) 확인 → 결과 보기
5. 포스터·홍보 글·영상 결과 → PNG 저장 / 글 복사 / 영상 저장
6. 내용 다시 수정, 새 작업, 이전 내용 되돌리기, 홈 이동, 기록 다시 열기

현재 전체 만들기에서 포스터 / 영상 / 둘 다를 선택할 수 있으며, 홍보 글은 항상 함께 제공된다. 단독 포스터·단독 영상은 해당 미디어만, 단독 홍보 글은 글만 제공한다. 세 채널을 동시에 일괄 생성하는 기능은 현재 없다.

### 2.2 기능 목록과 실제 동작

| 기능 | 확인된 동작 | 보존 계약 |
| --- | --- | --- |
| 로그인·가입 화면 | 이메일 형식·비밀번호 4자 이상 검증, 비밀번호 표시 전환, 진입 | 현재 체험 흐름 보존. 실제 계정 인증이라고 표시하지 않음 |

| 홍보 글 | 채널별 고정 문장 구조와 입력값 조합 | 글 전체와 확정 태그를 함께 복사 |
| 포스터 파일 | Canvas, 1080×1350 PNG | 실제 파일 생성·다운로드, 긴 문구 줄바꿈 |
| 영상 파일 | Canvas + MediaRecorder, 720×1280, 약 3초, MP4 또는 WebM | 지원 탐지, 취소·재시도, 형식별 실제 파일 |
| 결과 미리보기 | HTML/CSS 포스터와 사진 확대 효과 영상 | 재생·정지·원문 확인·결과 이동 유지 |
| 내 홍보물 | React 메모리에 입력 스냅샷 저장·다시 열기 | 결과 종류·선택 형식·채널·사진·입력·수동 태그 복원 |
| 새 작업 되돌리기 | 초기화 직후 이전 초안 1회 복원 | 새 입력·다른 기록·로그아웃 시 복원 만료 |
| 접근성 도움 | 기본 간편모드, 큰 글씨, 한국어 음성 안내 | 준비 취소·중지·타임아웃·미지원 안내 유지 |
| 이용 방법 | 구독·건당 방식 선택, 가격·수량 미정 | 선택 흐름 유지, 결제 가능하다고 표시하지 않음 |

중요한 한계:
- 실제 AI 분석·생성 API, 회원 인증, 결제 API는 연결되어 있지 않다.
- 사진은 제품 내용을 분석하지 않는다. 제품 정보는 일반적인 예시 문장으로 시작한다.
- 기록·초안·보기 설정은 메모리 상태다. 새로고침하면 사라진다.
- 결과 기록은 완성 파일 저장소가 아니다. 입력을 복원해 결과를 다시 보여 주는 구조다.
- 영상 미리보기는 저장될 영상 파일의 실제 재생이 아니다.
- 외부 SNS 자동 게시, 클라우드 저장, 일괄 다운로드, QR 생성은 현재 기능이 아니다.

### 2.3 기술 구조와 의존성

React 19 / React DOM 19, Vite 8, Tailwind CSS v4, TypeScript 5.7을 사용한다. Playwright는 개발 의존성으로 설치되어 있다. 런타임 의존성은 React 계열뿐이며 별도 라우터·상태 관리·컴포넌트 라이브러리·API SDK는 없다.

AGENTS.md에 언급된 Figma Make 플러그인·.mise.toml은 현재 vite.config.ts 및 파일 목록에서 확인되지 않았다. 현재 실제 설정을 기준으로 호환성을 보존하며, 감사만으로 도구를 추가하지 않는다.

App.tsx 약 2,820줄에 제작 화면, 데이터 가공, 파일 출력, 음성 안내, 기록·초안 상태가 함께 들어 있다. StudioScreens.tsx에는 로그인·홈·Shell이 분리되어 있다. 스타일은 Tailwind 클래스, index.css 전역 규칙, studio.css의 덮어쓰기 규칙으로 나뉜다.

장점:
- 불필요한 런타임 라이브러리가 적다.
- 사진 교체의 비동기 순서, 음성 취소, 수동 태그 보존 등 복구 로직이 구체적이다.
- 긴 한글·이모지 Canvas 줄바꿈은 별도 유틸리티로 분리되어 있다.
- 메뉴의 초점 제한·Escape 닫기·inert, 단계 제목 초점 이동, reduced-motion 처리가 존재한다.

## 3. 주요 UX/UI 문제

우선순위는 P0: 결과 신뢰·작업 보존, P1: 핵심 행동·접근성, P2: 시각 완성도·유지보수다. 아래는 모두 발견 사항 또는 검증이 필요한 위험이며, 사용자 테스트로 확정한 통계가 아니다.

| 우선순위 | 문제와 근거 | 사용자 영향 | 구체적 조치 |
| --- | --- | --- | --- |
| P1 | 첫 화면의 주요 버튼이 긴 3단계 안내 뒤에 있음. 기존 JSON에서 390px 폭 약 y=1372, 320px 폭 약 y=1631 | 하단 만들기로 바로 진입할 수 있지만 본문의 대표 행동은 긴 안내 뒤에 있어 시작 위치가 분산됨 | 첫 화면에 제목·사진 선택을 배치. 자세한 사용법은 입력 아래로 이동 |

| P1 | 간편모드에서 쉬운 표현은 제공하지만 Shell 메뉴의 ‘구독·건당 플랜’ 등은 사전 치환을 거치지 않음 | 화면마다 난이도가 달라짐 | 기본 UI 전체를 쉬운 한국어로 작성. 큰 글씨 설정은 별도 제공 |

| P1 | role=radio 버튼에 방향키·roving tabIndex 처리가 없음 | 키보드 사용자가 기대하는 라디오 동작과 다름 | native radio + label + fieldset/legend로 재구성 |
| P1 | 페이지·단계가 URL과 동기화되지 않음 | 뒤로가기가 이전 입력 단계로 돌아오지 않음 | history 기반 화면·단계 동기화. URL에는 사진·설명 같은 입력 데이터 제외 |
| P0 | 기록은 메모리에만 있고 ‘내 홍보물’ 명칭은 장기 보관처럼 느껴질 수 있음 | 새로고침 후 작업 손실·신뢰 저하 | 생성·결과·기록 위치에 임시 보관 범위를 안내. 기기 보관은 별도 확장으로 검토 |

| P1 | 결과 제목·완료 설명·예시 안내가 길게 반복됨 | 저장·복사 전 스크롤 부담 | 짧은 완료 안내 → 종류 이동 → 미디어/글 → 즉시 저장·복사 순서로 정리 |
| P1 | 홍보 글 단독도 사진을 요구하지만 글 템플릿은 사진을 사용하지 않음 | 글만 필요한 사람에게 불필요한 준비물 | 글 단독 경로에서 사진을 선택사항으로 바꾸는 UX 개선 검토. 미디어 경로 필수 조건 유지 |
| P1 | 세 설명 필드에 일반 예시 문장이 입력되어 있음 | 사진을 읽어 실제 상품 설명을 만든 것으로 오해할 위험 | ‘예시로 채우기’ 보조 행동과 구체적 예시·입력 도움 제공. 자동 분석으로 표현하지 않음 |
| P2 | 홈 카드 안에 안내 카드·강조 박스가 반복되고 단계 그림은 실사용 화면에서 보이지 않음 | 안내가 길고 서비스만의 기억점이 약함 | 직접 입력 영역과 여백 중심 구성, 단계별 역할을 설명하는 일러스트 3종 |
| P2 | CSS에 여러 팔레트·클래스 문자열 선택자·반복 덮어쓰기 존재 | 화면 간 일관성과 후속 변경 예측성 저하 | 의미 기반 토큰과 공통 Button / Field / Notice 도입 |
| P2 | @font-face는 ‘Noto Sans KR:Regular’ 등으로 등록되나 Canvas는 ‘Noto Sans KR’ 요청 | 기기에 따라 화면과 출력 파일의 폰트가 달라질 가능성 | 실제 등록 패밀리 통일, 폰트 로딩 후 Canvas 출력 |
| P2 | 사진 선택 영역의 빈 상태 min-height가 300px | 휴대전화에서 종류·채널·다음 행동을 밀어냄 | 읽기 쉬운 선택 버튼 중심으로 높이를 줄이고 사진 선택 후 확인 상태로 교체 |

대비 확인 사례: 현재 .studio-eyebrow의 #90644C와 안내 배경 #F5EDDF는 계산상 약 4.39:1이다. 기본 스타일 15px 굵은 안내 글에서는 일반 텍스트 4.5:1 목표에 못 미친다. 간편모드·실제 cascade에서 크기가 달라질 수 있으므로 전 화면 위반이라고 단정하지 않는다.

모바일 하단 메뉴·1단계 고정 CTA·키보드 대응은 이미 구현되어 있다. 따라서 ‘키보드에 무조건 가려진다’고 판단하지 않는다. 실제 Android/iOS 키보드와 짧은 화면에서의 가림·포커스는 후속 실기기 검증 대상으로 남긴다.

2+1 결과 카드 배열 문제는 이미 해결되었다. 결함 목록에서 제외한다. 기존 단일 열·넓은 화면 다열 배치, 긴 문구 원문, 카드별 조작, 다음 결과 이동은 회귀 보존 대상이다.

## 4. 세 관점의 독립 평가

별도 런타임 에이전트나 실제 시니어 인터뷰를 수행한 것으로 표시하지 않는다. 같은 자료를 서로 다른 평가 기준으로 검토했다.

### 시니어 사용자 UX 옹호자

좋은 점: 큰 글씨 기본값, 한글 안내, 사진 교체 실패 복구, 선택 검색어 접기, 되돌리기, 결과 이동 링크.

핵심 판단: 읽기 쉬운 화면은 갖추었지만 ‘지금 누를 것’보다 ‘서비스 설명’이 먼저 나온다. 로그인·종류 선택·채널 선택·설명 3개를 연속 판단하게 만들며, 용어와 음성이 일치하지 않는다.

권고: 첫 화면에 사진 선택, 한 화면의 대표 행동 하나, 선택의 이유를 한 줄로 설명, 필수 입력 옆 도움, 조작 후 분명한 상태, 수정해도 기존 입력 유지. ‘시니어용’이라는 낙인성 표현을 UI에 쓰지 않는다.

### 시니어 프런트엔드 엔지니어

좋은 점: 기능 의존성이 적고 비동기 복구·수동 태그 보존·초점 처리가 마련되어 있다.

핵심 판단: 새로운 디자인을 기존 App.tsx에 계속 덧붙이면 파일 출력·취소·기록 복원과 화면 상태가 함께 흔들린다. 결과를 ‘봤다’, 파일이 ‘준비됐다’, 다운로드를 ‘요청했다’는 서로 다른 상태다.

권고: 데이터와 출력 계약을 먼저 고정하고, 파일 생성·음성·업로드·초안 상태를 훅/모듈로 분리한다. 사용자 정의 라디오는 native input으로 교체한다. 현재 스택을 유지하고 새 라이브러리는 필요성을 입증한 경우만 추가한다.

### 크리에이티브 디자인 디렉터

좋은 점: 홍보잇다 이름, 가게 작업실 콘셉트, 따뜻한 표면과 진한 세이지 버튼은 활용 가치가 있다.

핵심 판단: 현재도 차분하지만 카드 중첩·긴 안내·이모지와 선 아이콘의 혼용 때문에 상용 서비스의 통일감이 약하다. 파스텔을 더 넣는 것만으로 프리미엄이 되지 않는다.

권고: 주요 작업 도구를 가장 앞에, 안내는 여백과 짧은 문장으로 구분한다. 제한된 파스텔·남색·일관된 선 아이콘, 작업을 설명하는 성숙한 인물 일러스트를 사용한다.

충돌 해결:
- 큰 일러스트가 사진 입력을 밀면 일러스트를 축소하거나 아래로 이동한다.
- 큰 글씨로 화면이 길어지면 글자 크기를 줄이기보다 중복 설명과 카드 중첩을 줄인다.
- 균형 있는 카드 높이가 미리보기·조작을 작게 만들면 조작 가능성을 우선한다.
- 구현을 단순하게 만들더라도 태그 수동 편집·취소·복원 기능은 제거하지 않는다.

## 6. 제안하는 재설계 방향

### 6.1 정보 구조

핵심 탐색은 홈 / 만들기 / 내 홍보물 세 개를 유지한다. 모바일은 텍스트와 아이콘을 함께 표시하는 하단 탐색, 데스크톱은 축소된 왼쪽 탐색으로 일관성을 유지한다.

단독 제작은 별도 프로세스가 아니라 하나의 만들기 흐름에 전달되는 제작 모드다. 홈에는 ‘만들 종류’ 선택과 세 단독 진입을 제공하고, 전체 메뉴에서도 접근 가능하게 유지한다. 이용 방법과 로그인·회원가입은 보조 탐색이다. 실제 플랜 정보가 없는 동안 요금제를 판매하는 인상을 주지 않는다.

홈·제작은 같은 PhotoInput과 공통 상태를 공유한다. 홈에서 고른 사진을 제작 1단계에서 다시 고르게 하지 않는다. 사진 확인에 성공하면 설정을 이어가고, 실패하면 같은 자리에서 회복한다.

### 6.2 화면별 구성과 문구

첫 화면:
- 제목: ‘우리 가게 홍보물, 사진 한 장으로 시작하세요.’
- 설명: ‘사진과 설명을 넣으면 홍보 이미지, 짧은 영상, 홍보 글을 만들 수 있어요.’
- 주요 행동: ‘제품 사진 선택하기’
- 파일 안내: ‘사진 한 장 · 20MB 이하’
- 종류 기본 선택: ‘이미지·영상·글 모두’ — 기존 both + copy
- 보조 선택: ‘이미지만 / 영상만 / 글만’
- 체험 안내: ‘현재는 사진과 입력한 내용을 조합한 예시를 만들어요.’
- 입력 영역 아래: 짧은 3단계 안내, 선택 도움말, 최근 결과 진입

‘글만’은 단독 copy에 대응한다. ‘이미지만’·‘영상만’은 단독 poster·video에 대응한다. 전체 만들기 안에서 이미지+글 또는 영상+글을 만들 수 있는 기존 조합은 ‘함께 만들 결과’ 설정으로 보존한다. ‘이미지만’이라고 쓰고 홍보 글을 추가 출력하는 모순을 만들지 않는다.

1단계 — 사진과 종류:
- 사진 선택 → 정상 확인 → 교체 버튼
- ‘어떤 홍보물이 필요하세요?’
- ‘어디에 올릴까요?’와 채널별 한 줄 안내
- 선택값은 추천 기본값임을 명확하게 하고 언제든 변경 가능
- 주요 행동: ‘설명 입력하기’
- 실패: ‘사진을 열지 못했어요. JPG 또는 PNG 사진을 다시 선택해 주세요.’
- 교체 실패 시: ‘기존 사진은 그대로 사용할 수 있어요.’

2단계 — 설명:
- 작은 사진·선택 종류·홍보할 곳을 요약하고 각각 수정 가능
- ‘제품을 간단히 소개해 주세요’
- 필드: ‘어떤 제품인가요?’ / ‘꼭 알리고 싶은 특징은 무엇인가요?’ / ‘어떤 손님께 추천하나요?’
- 입력 예시: ‘매장에서 직접 굽는 단팥빵’ / ‘당일 만든 제품만 판매해요’ / ‘간식을 찾는 동네 손님’
- 기존 필수 세 필드는 유지. 구조 변경 없이 임의로 필수값을 삭제하지 않음
- 실제 상품 사실을 미리 입력했다고 오해하지 않도록 placeholder·예시 채우기 구분
- ‘검색어(#) 바꾸기 · 선택’과 현재값 미리보기 유지
- 주요 행동: ‘이 설명으로 홍보물 만들기’
- 안내: ‘사진을 자동 분석한 설명이 아니에요. 제품에 맞게 입력해 주세요.’

진행 상태:
- 입력 준비, 파일 준비, 저장 요청을 별도로 표현
- 작업이 즉시 끝나면 가짜 대기 화면을 만들지 않음
- 실제 영상 준비에는 ‘영상 파일을 준비하고 있어요’와 취소 행동
- 완료 전까지 저장 버튼 중복 요청 방지
- 지원하지 않으면 ‘이 기기에서는 영상을 저장할 수 없어요. 다른 브라우저에서 다시 시도해 주세요.’와 기존 결과 보존

결과:
- 제목: ‘홍보물이 준비됐어요.’
- 짧은 설명: ‘내용을 확인한 뒤 파일을 저장하거나 글을 복사해 주세요.’
- ‘이미지 / 홍보 글 / 영상’ 이동 링크는 기존처럼 이동용이며 다른 결과를 숨기지 않음
- 카드마다 명확한 이름, 필요한 미리보기, 한 개의 대표 행동
- ‘이미지 파일 저장하기’ / ‘홍보 글과 검색어 복사하기’ / ‘영상 파일 저장하기’
- 파일 준비 완료: ‘파일이 준비됐어요.’
- 저장 요청 이후: ‘저장을 요청했어요. 기기의 다운로드 목록을 확인해 주세요.’
- 브라우저가 실제 저장 성공을 보장하지 못하므로 ‘기기에 저장 완료’라고 단정하지 않음
- 원문 펼치기·긴 내용 축약 안내 유지
- 수정·새 작업·홈 이동을 중요도에 따라 구분
- 새 작업 뒤 한 번 되돌리기 유지

내 홍보물:
- 사진 썸네일·설명·종류·채널·날짜로 쉽게 찾기
- ‘이 창에서 만든 홍보물이에요. 창을 닫거나 새로고침하기 전에 필요한 파일을 저장해 주세요.’
- 빈 상태에 ‘첫 홍보물 만들기’ 행동
- 영구 보관을 실제로 구현하기 전에는 계정 저장·자동 보관 완료라고 표시하지 않음

### 6.3 시니어 친화 접근성

큰 글씨와 쉬운 한국어를 기본값으로 유지한다. ‘간편모드’의 효과를 모르는 문제를 줄이기 위해 보기 설정 안에서 ‘글씨 크기: 기본 / 크게’처럼 실제 효과를 설명한다. 현재 일반·큰 글씨 선택과 화면 읽어주기는 유지한다. 작은 글씨 사용자도 쉬운 한국어를 받도록 한다.

- 본문 18–20px, 큰 글씨 22px, line-height 1.6–1.7
- 모바일 제목 28–32px, 데스크톱 36–44px
- 버튼·중요 입력 높이 56px 이상, 큰 글씨 주요 조작 60px
- 모든 중요 터치 영역 최소 44×44 CSS px, 대체로 48px 이상
- 선택 상태는 색·체크 표시·문구를 함께 사용
- native radio, 명확한 label, fieldset/legend, 오류의 aria-describedby·aria-invalid
- 페이지당 최상위 h1, 단계 변경 후 제목 초점, 본문 바로가기
- 취소·오류·복사 결과는 읽을 수 있는 status로 전달
- 화면 읽어주기는 사용자가 시작하며 스크린리더를 대체한다고 주장하지 않음
- 메뉴 초점 제한·Escape·inert, reduced-motion 기존 동작 유지
- 화면의 버튼 이름과 음성 안내를 일치시킴
- 가상 키보드 표시 시 CTA·탐색이 입력란을 가리지 않게 함

텍스트 대비는 일반 글자 4.5:1, 큰 글자 3:1 기준으로 검증한다. 근거: [W3C 대비 설명](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).
44px 이상 목표는 이 프로젝트의 시니어 친화 설계 기준이다. WCAG 2.2 AA의 Target Size (Minimum)는 예외·간격 조건을 포함한 24px 기준이므로 이를 44px 의무 기준으로 잘못 설명하지 않는다. 근거: [W3C 터치 영역 설명](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).

값은 제안이며 실제 hover·focus·disabled·오류 상태까지 검증한 최종 디자인 시스템이 아니다. 파스텔은 배경·삽화에, 읽기·조작은 진한 색에 사용한다.

간격은 4 / 8 / 12 / 16 / 24 / 32 / 48 / 64px. 모바일 좌우 여백 16–20px, 입력 읽기 폭 약 680–760px, 전체 결과 폭 약 1,160px을 시작점으로 사용한다. 둥근 모서리는 입력·버튼 12–14px, 주요 표면 20–24px, 그림자는 꼭 필요한 표면 구분에만 사용한다.

한글 폰트는 한 패밀리와 실제 사용 굵기로 정리하고 시스템 fallback을 둔다. 기존 Noto Sans KR을 우선 검토한다. font-display와 Canvas 폰트 준비를 함께 설계한다.

### 6.5 Corporate Flat Vector Illustration

기존 선 아이콘을 작업 조작에 유지·정리하고, 사람과 사물을 함께 쓰는 독자 SVG 일러스트 3종을 만든다.

1. 사진 선택: 성인 가게 운영자, 휴대전화, 제품 사진
2. 설명 입력: 운영자와 설명 입력칸·수정 도구
3. 홍보물 저장: 운영자와 이미지·글·영상 결과, 저장 표시

통일 규칙:
- 2D 평면, 남색 윤곽선, 민트·피치·하늘색 중심의 제한된 색상
- 같은 viewBox와 비례, 기본 선 굵기 2px 기준
- 성숙한 인물, 과장된 표정·유아적 캐릭터·3D·강한 질감 제외
- 그림 안에 중요한 한국어 문구를 박지 않고 화면의 실제 텍스트로 설명
- 행동을 설명하는 경우 대체 텍스트, 주변 설명과 중복되는 그림은 장식 처리
- 모바일 약 96–128px에서 읽히는 구성, 첫 화면 입력을 밀지 않음
- 파일명을 체계적으로 관리하고 원본 제작·라이선스 근거 기록
- 단계 설명은 둥근 흰색 표면과 짧은 문장으로 구성하되 거대한 안내 카드 3개를 첫 행동 앞에 두지 않음

Phase 1에서는 자산을 생성·적용하지 않았다.

### 6.6 반응형 결과 배치

모바일은 한 열을 기본으로 유지한다. 미리보기의 비율을 고정하고 저장·복사 조작을 너무 작은 열에 넣지 않는다.

넓은 화면은 실제 콘텐츠 영역 폭과 결과 수를 기준으로 열을 결정한다. 3개 결과는 충분한 폭에서 균형 있는 3열, 부족한 폭에서는 읽기 쉬운 한 열을 우선한다. 2개는 가능한 폭에서 2열로 보인다. 이미 해결된 2+1 문제를 다시 열지 않는다.

현재 제품의 결과 수는 최대 3개다. 공통 ResultGallery는 더 많은 수에도 빈칸·넘침 없이 동작하도록 확장 가능하게 설계하되, 현재 기능을 임의로 다중 생성 기능으로 바꾸지 않는다. 카드의 액션 정렬을 위해 긴 글 전체를 잘라 버리지 않는다.

### 구현 후 검증 기준

- 폭 320 / 375 / 390 / 430 / 768 / 1024 / 1440px에서 의도하지 않은 가로 스크롤·잘림·조작 가림 없음
- 일반/큰 글씨, 실제 브라우저 200% 확대, 짧은 높이, 긴 한글·무공백·이모지 입력
- 실제 Android/iOS 파일 선택·다운로드·영상 형식·가상 키보드
- native radio 방향키, Tab 순서, 메뉴 닫기, 페이지·단계·오류 초점
- 스크린리더와 실제 한국어 음성 안내. 모의 음성 검사는 실제 음질 검증과 구분
- 전체 형식 3종과 단독 제작 3종, 채널 3종의 문구·미디어 스타일
- 사진 오류·용량 초과·디코딩 실패·지연 후 재선택 시 기존 사진 유지
- 검색어 자동 갱신과 수동 보존, 채널 변경, 기록 복원
- PNG 실제 해상도·내용·미리보기 일치, 영상 실제 재생·시간·형식·취소·미지원 회복
- 글 복사에는 원문과 확정 태그 포함
- 새 작업 되돌리기와 만료 조건, 뒤로가기에서 작성 중 값 보존
- 기록의 임시 보존 범위를 생성·결과·목록에 정확히 표시

기존 verify:ui / verify:readability / verify:studio / verify:zoom / verify:recovery를 기준으로 사용한다. 특히 verify:studio는 현재 ‘안내 뒤에 CTA’ 위치를 통과 조건으로 검사하므로 새 UX 목표에 맞게 바꾸어야 한다. 이름만 바꾸고 기존 위치 검사를 통과시키는 방식으로 완료하지 않는다.

빌드와 TypeScript 검사, 기능에 맞는 회귀 검증 후 실제 사용자·기기 검토를 수행한다. 기존 통과 기록을 이번 변경의 통과 결과로 재사용하지 않는다.
