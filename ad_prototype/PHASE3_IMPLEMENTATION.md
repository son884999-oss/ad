# 홍보잇다 Phase 3 구현·검증 보고서

완료일: 2026-10-09. 최종 첨부 요청의 **COMPLETE PRODUCT EXPERIENCE RECONSTRUCTION** 범위를 실제 React 프로젝트에 구현했다. `AGENTS.md`, `DESIGN_MASTER.md`, Phase 1 분석과 Phase 2 구현·디자인 시스템·채널 전략·에셋 계획을 검토했다. React 19 / Vite 8 / TypeScript / Tailwind CSS v4 구조와 기존 기능을 유지했다.

## 1. 주요 UI/UX 변경 사항

사이드바 중심 작업 화면을 모바일의 ‘홈 → 만들기 → 내 홍보물’ 구조로 재구성했다. PC에서는 같은 세 가지 목적지를 헤더에 배치했다. 단독 포스터·영상·글 만들기와 요금제·로그인 체험은 홈 바로가기 또는 전체 메뉴에서 계속 접근할 수 있다.

작업 흐름은 사진, 설명, 결과 창의 세 단계다. 처음부터 채널과 검색어를 모두 결정하지 않아도 진행할 수 있다. 사진 화면을 `PhotoStep`, 진행 표시를 `StepProgress`, 공통 도형 아이콘을 `Icon`, 선택형 알림을 `FeedbackProvider`와 `FeedbackSettings`로 분리했다. 기존 파일 생성·기록·문구 로직을 장식용 화면으로 교체하지 않았다.

## 2. 홍보잇다 브랜드 유지

공식 명칭 **홍보잇다**를 헤더, 홈 주요 문구, 홈 이동 버튼의 접근성 이름, 로그인, 푸터에 유지했다. `index.html`의 한국어 제목·description·Open Graph·favicon은 Phase 2 상태를 그대로 보존했다. 이번 단계에서 이름이나 metadata를 다른 브랜드로 바꾸지 않았다.

## 3. 홈페이지와 첫 화면

홈의 주요 문구는 ‘사진 한 장으로 우리 가게를 알려요.’이며, ‘포스터·짧은 영상·홍보 글을 차근차근 함께 만들어요.’로 기능을 설명한다. ‘홍보물 만들기’가 유일한 주 행동이다.

390px 모바일에서는 짧은 소개 → 시작 버튼 → 큰 대표 이미지 순서다. PC에서는 설명과 넓은 결과 화면 일러스트를 나란히 배치했다. 7개 검증 너비 모두 시작 버튼의 아래쪽이 화면 상단에서 700px 이내에 있고, 대표 이미지도 첫 화면에서 시작하는 것을 확인했다.

‘글씨·읽어주기·알림 설정’은 이름이 보이는 펼침 영역으로 정리했다. 간편모드는 기본 켜짐이며 기능을 삭제하지 않았다. 체험 서비스 안내는 대표 이미지 아래에 유지했다. 홈의 세 단계 설명은 모바일에서 세로 연결선, 큰 화면에서 가로 연결선을 사용한다.

## 4. 메인 히어로 제작·배치

공식 `imagegen` 스킬에 따라 실제 사용 가능한 내장 `image_gen` 도구로 새 대표 장면을 제작했다. Phase 2 사장님 이미지에서 인물과 색상을 참조하고, 큰 결과 창을 중심으로 새 구도를 만들었다. 이후 같은 생성 결과를 참조해 주변 번짐을 줄이고 밝은 민트 단색 배경으로 다듬었다. 별도 유료 API나 CLI 생성은 사용하지 않았다.

민트 앞치마의 사장님이 사진을 선택하고, 다른 사장님이 포스터·세로 영상·글이 놓인 큰 화면을 소개하는 구성이다. 성숙한 인물, 남색 외곽선, 민트·하늘색·피치 계열을 사용한다. 타사 일러스트를 복제하지 않았다. 결과물은 Corporate Flat 스타일의 **raster 이미지**이며 편집 가능한 SVG 원본이라고 표시하지 않는다.

선택한 PNG는 1536×1024다. 홈페이지의 실제 `<img>`에 WebP와 `srcSet`을 연결하고, `fetchPriority="high"`, 고정 비율, 내용 설명 대체 텍스트를 지정했다. 모바일에서도 이미지를 잘라내지 않는다.

## 5. 사진 → 설명 → 결과 창

| 단계 | 실제 동작 | 다음 행동 |
|---|---|---|
| 사진 | 파일 종류·20MB 제한·이미지 해석 확인, 사진 미리보기, 만들 결과 선택 | 사진 확인하고 다음 |
| 설명 | 제품 설명·강조할 특징·주요 고객 수정, 선택한 사진과 형식 확인 | 이 내용으로 결과 보기 |
| 결과 창 | 기존 규칙 기반 예시 결과, 포스터·글·영상 미리보기 | 저장·복사·수동 업로드 안내 |

설명란마다 자연스러운 한국어 예시를 추가하고 `aria-describedby`로 연결했다. 빈 필드는 `aria-invalid`와 기존 상태 안내로 알리고 결과 이동을 막는다. 수동 검색어 수정·추천 교체 기능은 선택 영역에 보존했다.

파일 확인 중에는 실제 `uploadPending`을 사용한다. 결과 생성은 기존 동기 처리이므로 가상의 AI 분석 단계나 진행률을 추가하지 않았다. 완료한 단계 버튼으로 돌아가도 App에 보관된 사진·설명·채널·검색어가 유지된다.

## 6. 연결형 진행 표시와 반응형

`StepProgress`는 실제 `step` 값으로 완료·현재·다음을 구분한다. 완료는 체크와 ‘완료 · 수정’, 현재는 채워진 원과 ‘현재 단계’, 다음은 외곽선과 ‘다음 단계’로 표시한다. 색상만으로 상태를 구분하지 않는다.

세 노드를 선으로 연결하고 실제 완료 구간만 짙은 색으로 바꾼다. 모바일에서는 ‘사진 / 설명 / 결과 창’, 640px 이상에서는 확장 이름을 표시한다. 마지막 노드는 결과 창 모양의 SVG다. 현재 단계에는 `aria-current="step"`, 이전 단계에는 구체적인 돌아가기 버튼 이름을 지정했다. 다음 단계는 이동 버튼이 아니다.

## 7. 버튼·터치 인터랙션

주요 버튼·선택 영역은 48px 이상, 간편모드 주요 버튼은 60px 이상 높이를 기본으로 한다. 포스터·영상·둘 다 선택은 native radio와 큰 label 영역을 사용한다. 선택은 테두리·배경·‘선택됨’ 글자로 확인한다. 포커스는 명확한 외곽선, 누름은 140ms의 작은 위치 변화로 표현한다.

사진을 고르기 전에는 비활성 ‘다음’ 영역을 문서 흐름에 놓는다. 사진이 준비되면 모바일에서 다음 버튼을 하단 메뉴 위에 고정한다. 실제 캡처 검토 중 사진 선택 안내를 가리던 부분을 발견해 수정했으며, 작은 화면에서 `elementFromPoint`로 사진 선택 문구가 가려지지 않는 것도 검증했다.

## 8. 화면 전환

실제 단계 패널을 230ms 페이드로 전환한다. 별도의 대기 단계나 인위적 완료 지연은 없다. 고정 버튼의 위치 기준을 바꾸지 않도록 패널에는 transform 이동을 사용하지 않는다.

`prefers-reduced-motion: reduce`에서는 전환·애니메이션과 버튼의 위치 변화를 제거한다. 상태 문구·선택 표시·단계 이동은 그대로 작동한다. 새 애니메이션 라이브러리는 추가하지 않았다.

## 9. 효과음과 설정

효과음은 **기본 꺼짐**이다. 설정 영역에서 직접 켜고 ‘효과음 들어보기’로 확인할 수 있다. 사용자 동작 전에는 `AudioContext`를 만들거나 재생하지 않는다. 켜짐 설정을 복원해도 페이지 로드만으로 소리를 내지 않는다.

Web Audio의 sine oscillator로 짧은 원음을 직접 합성한다. 업로드 확인은 587.33Hz, 일반 완료는 523.25Hz, 결과 준비는 523.25Hz와 659.25Hz 두 음이다. 각 음은 160ms, 최대 gain은 0.045이며 페이드 인·아웃을 준다. 일반 이동 버튼마다 소리를 붙이지 않았다.

실제 사진 해석 성공, 결과 준비, 복사 성공, 생성 파일의 브라우저 다운로드 요청에 연결했다. 다운로드 소리는 파일 시스템 저장 완료를 확인했다는 의미가 아니다. 숨겨진 문서 또는 읽어주기 재생 중에는 효과음을 생략하고, 180ms 안의 중복 알림을 억제한다. 끄면 재생 중인 oscillator를 중단한다.

설정은 `localStorage`의 `hongboitda.feedback.v1`에 저장한다. 저장 실패 시 현재 창의 설정은 유지하고 ‘설정은 이 창에서만 유지돼요.’라고 안내한다. 로그인은 필요 없다.

## 10. 진동 지원

진동도 **기본 꺼짐**이다. `navigator.vibrate`의 존재를 확인하며, 없는 브라우저에서는 비활성 스위치와 지원하지 않는다는 설명을 제공한다. 사용자가 켰을 때 사진 확인·결과 준비에만 20ms를 요청한다. 끄면 `vibrate(0)`으로 취소한다. 지속 진동이나 복잡한 패턴은 없다.

API가 있다는 사실이 실제 진동을 보장하지는 않는다. iOS Safari 지원을 가정하지 않았으며, 알림 API가 없는 경우에도 사진→결과 흐름이 완주되는 것을 확인했다. 진동 호출은 테스트에서 안전하게 대체해 확인했으며 실물 기기의 진동을 확인했다고 주장하지 않는다.

## 11. 추가·재사용 에셋

이번 단계의 추가 일러스트는 대표 장면 1종과 그 최적화 파일 2개다. 기존 `step-photo`, `step-details`, `step-ready`는 홈의 보조 단계 안내와 빈 상태·결과 안내에 재사용했다. 작은 단계 이미지를 대표 이미지와 같은 크기로 키우지 않았다.

단계 체크·결과 창·사진·영상·글·다운로드·설정 등 단순 UI 표시는 `Icon.tsx`의 일관된 SVG로 관리한다. 주요 형식 선택과 결과 헤더의 장식 이모지를 교체했다. 소리 파일이나 타사 음원은 사용하지 않는다.

## 13. 반응형 검증

Windows의 Playwright + headless Edge에서 320 / 375 / 390 / 430 / 768 / 1024 / 1440px를 확인했다. 각 너비에서 홈·사진·설명·결과·설정의 총 35개 화면 상태에 가로 넘침이 없고, 표시된 본문 버튼의 높이가 44px 이상이었다. 단계 상태와 사진·설명 보존, 처음의 채널 영역 접힘, 기본 알림 꺼짐도 확인했다.

320 / 390 / 1440px 캡처를 `ui-review/phase3/`에 저장했다. 실제 이미지 파일을 열어 모바일 홈·사진·설명과 PC 홈·결과를 검토했다. 결과 화면은 좁은 화면 1열, 1440px에서 결과 개수에 맞는 2열 또는 3열이라는 기존 규칙을 유지한다. 이미 해결된 2+1 배치를 새 버그로 취급하지 않았다.

이 검증은 실물 모바일 기기 또는 전체 접근성 인증을 대신하지 않는다. 전체 페이지 캡처에는 고정 하단 메뉴가 최초 viewport 위치에 찍히므로, 긴 이미지 전체에서 메뉴가 중간에 보이는 것은 캡처 방식의 특성이다. 실제 스크롤·터치 대상 가림도 별도로 확인했다.

## 14. 홍보 플랫폼 선택

Phase 2의 기본 추천 네이버 스마트플레이스 → 카카오톡 채널 → 인스타그램과 업종별 추천 재정렬을 유지했다. 초기 선택은 여전히 **파일만 저장하기**다. 사진 화면의 ‘홍보할 곳 고르기 · 선택 사항’을 펼치면 현재 선택, 추천, 추가 채널에 접근한다.

네이버 블로그·당근 비즈프로필·유튜브 쇼츠·엑스·쓰레드를 포함한 기존 9개 선택, 채널별 글·검색어, 결과의 수동 게시 안내를 보존했다. 추천 변경이 사용자의 실제 선택을 바꾸지 않는다. 외부 링크는 수동 이동이며 계정 연결·자동 게시 버튼으로 표현하지 않았다. 새로운 외부 인증이나 게시 작업은 수행하지 않았다.

음성 복구 일부는 mock이며, 새 효과음 테스트는 실제 Web Audio oscillator 생성·주파수·재생 호출을 관찰했다. 진동은 실제 하드웨어 대신 API 호출을 관찰했다. 사람의 청감·손으로 느끼는 진동은 검증하지 않았다.

기존 검증 스크립트는 설정/채널을 펼치는 진입 동작, 제거된 사이드바 대신 상단 메뉴, 프로젝트 내부 이미지 fixture에 맞춰 갱신했다. 기능 검증 조건을 삭제해 통과시키지 않았다. 초기 캡처에서의 버튼 가림은 실제 구현을 수정했다. oxfmt 0.2가 한 줄 type 구분자를 잘못 출력한 부분은 여러 줄 type으로 바꾼 뒤 타입 검사·build를 다시 통과했다.

최종 build의 JS는 262.78kB, gzip 81.40kB이며 CSS는 51.18kB, gzip 10.97kB다. 새로운 런타임 의존성을 설치하지 않았다.

## 17. 세 가지 전문가 관점 검토

아래는 세 관점으로 수행한 자체 검토이며 별도의 전문가 인터뷰나 독립 에이전트 심사를 수행했다는 의미가 아니다.

| 관점 | 발견한 문제 | 실제 반영 | 남은 검증 |
|---|---|---|---|
| 시니어 사용자 UX | 설정·채널 결정이 첫 행동보다 앞서고, 비활성 다음 버튼이 사진 선택을 가림 | 설정과 채널 접기, 파일만 저장 기본값, 사진 전에는 다음 버튼 고정 해제, 실제 가림 검사 | 실물 휴대전화에서 첫 행동·오류 회복 관찰 |
| 시니어 프론트엔드 | 입력·레이아웃·알림 관심사 혼재, transform 전환이 fixed 위치에 영향 | 책임별 컴포넌트 분리, App 상태 보존, opacity 전환, API 존재 검사와 실패 처리, 회귀 검증 | 출력 렌더러 통합, 영구 저장 설계 |

## 18. Phase 4 우선순위

1. **출력물 품질**: 실제 상품 사진 fixture로 포스터 HTML 미리보기와 Canvas PNG의 배치·글자·색상을 일치시키고, 긴 한글의 줄바꿈과 안전 여백을 검증한다. 영상은 인코딩된 실제 파일 미리보기와 결과 화면의 차이를 줄인다.
2. **실기기와 시니어 사용성**: iOS Safari·Android Chrome에서 사진 선택, 키보드, 안전 영역, 저장 후 파일 찾기, 수동 게시까지 관찰한다. 실제 청감과 가능한 기기의 진동 강도를 확인한다. TalkBack/VoiceOver 검증을 추가한다.
3. **시각 정교화**: 대표 이미지의 남은 내부 음영·선 굵기, 홈 보조 섹션 간격, 빈 기록·요금제·로그인 체험의 일관성을 검토한다. 충분한 에셋은 재사용하고 목적 없는 장식을 늘리지 않는다.
4. **채널별 결과 적합성**: 실제 정책·규격에 맞춘 비율·문구 길이·영상 조건 검증과 업종별 기본값을 설계한다. 자동 게시가 필요하면 인증·권한·서버 token 관리·게시 전 확인을 별도 구현한다.
5. **작업 저장**: 새로고침 후 초안·기록 복원, 이미지 저장 용량·실패·삭제·만료를 다룬다. 현재 알림 설정만 기기에 저장된다는 점과 구분한다.

이번 첨부 요청이 정의한 Phase 3는 제품 경험 재구성이므로, Phase 2 보고서에서 후속 후보로 제시했던 렌더러 통합·영구 저장·외부 인증까지 완료했다고 확대해 보고하지 않는다.

## 19. 미구현 기능과 기술적 한계

현재 실제 AI 분석·생성, 외부 계정 인증·자동 게시, 결제·회원 백엔드, 영구 기록 저장은 없다. 기존 로그인·요금제는 체험 화면이고, 문구는 규칙 기반 예시다. 영상은 기존 사진 기반의 짧은 예시이며 전문 영상 편집이나 음성 합성을 새로 제공하지 않는다. 저장된 결과의 외부 플랫폼 수용을 보장하지 않는다.

알림은 선택적 보조 기능이다. 브라우저 자동 재생 정책·기기 설정·탭 상태·진동 하드웨어에 따라 실제 출력이 제한될 수 있으며, 완료 안내와 모든 작업은 화면으로도 사용할 수 있다. Safari 실기기, 실제 스크린리더, 사람의 효과음 청취는 아직 확인하지 않았다.

기술 판단에는 실제 접근한 [Web Audio 권장 사용법](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices), [Vibration API](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/vibrate), [동작 줄이기 미디어 쿼리](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)를 참고했다. 외부 디자인 사이트를 이번 단계에 새로 시각 검토했다고 주장하지 않는다. 디자인 원칙과 채널 판단은 기존 Phase 1·2의 조사 결과를 이어 사용했다.
