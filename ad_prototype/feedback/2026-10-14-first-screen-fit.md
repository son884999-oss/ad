# 첫 화면과 세 입력칸 배치 재검증

2026-10-14 KST. PR #11 병합 후 사용자가 홈·메뉴·정보 입력의 과도한 스크롤과 큰 빈 설명 칸을 지적했다. 마지막 요청의 명칭은 **상품 이름 / 가게 이름 / 소개 및 알리고 싶은 점**이다. 상품 이름만 필수다.

## 관찰한 문제와 수정

| 문제 | 실제 영향 | 수정 |
| --- | --- | --- |
| 홈의 큰 이미지와 여백 | 360×640에서 3단계 끝727.5px, 메뉴 시작559px로 약169px 초과 | 제목32→28px·본문20→18px·로고144→132px 등 약85~90% 조정, 이미지 높이를 남은 화면에 맞춤. 원본 이미지·브랜드 보존 |
| 메뉴의 긴 생성 버튼과 열린 설정 | 기본 목적지 아래로 스크롤해야 함 | 생성 4개를 2열로 배치, 버튼 면적 축소·68px 높이 유지. 설정 기본 접힘과44px 진입 유지, 긴 설정은 펼쳐 사용 |
| 소개·알릴 점의 분리된 큰 입력 | 상품·가게·소개와 생성 버튼을 동시에 보기 어려움 | 세 칸으로 통합. 소개는 한 줄·52px 수준에서 시작하며 입력·줄바꿈·폭·글씨모드에 따라 자연 확장·축소 |
| 반복 안내와 긴 placeholder | 빈 칸인데도 설명이 두 줄 높이가 됨 | 짧은 예시, 중복 안내는 접근성용으로 유지. 필수 오류는 입력 이름 옆에 표시 |
| 작은 휴대전화의 결과 저장 | 이미지·영상 아래 저장 버튼이 메뉴보다 아래 | 같은 미디어 규격을 남은 높이에 맞춤. 저장·복사 공통 규격, 읽기 바·탭·보조 동작 간격 조정 |

이전 초안에 분리된 소개·알릴 점이 있으면 통합 칸에 함께 표시한다. 새 입력은 기존 `details` 구조를 사용하므로 API·Canvas·영상 생성 알고리즘을 재구성하지 않는다. 뒤로 가기·초안·출력 선택·문구 후순위와 하단 메뉴를 유지한다.

## 실제 검증

- `verify:screen-fit`: 360×640,390×693,390×844,430×760,430×844,768×1024,1440×900 × 일반·간편 모드. 홈, 기본 메뉴, 빈/첨부 사진, 빈/상품 이름 단독 정보, 이미지/영상 저장의 **14개 프로필·118개 화면 경계(개별 이미지·영상·문구 제작의 정보 입력 6개 상태 포함)**를 확인한다.
- 정보 칸은 처음44px 이상·58px 이하. 한 줄 → 긴 문장·줄바꿈 → 삭제 후 한 줄로 복귀하고 입력 내용이 잘리지 않는지 검사한다.
- 독립 블랙박스 검토: 홈·빈/첨부 사진24개 상태, 360×640·390×693의 정보12개 상태, 확대·삭제·글씨 모드·320px 폭 변경, 실제 결과 내용·파일과 입력 보존을 확인했다.
- 기존 `verify:mobile-flow`, `verify:submission`, `verify:results`, `verify:usability`를 새 입력 이름과 기본 접힘 설정에 맞춰 재검증했다. 각각 14개 시나리오·12개 프로필·14개 프로필·20개 프로필을 통과했다. 분리된 테스트 페이지 밖에 모의 응답을 추가하지 않는다.
- TypeScript·Vite 빌드·문서 링크·신규 스크립트 구문/형식과 최종 diff를 검사해 통과했다. 별도 lint 설정은 없다.

선택하지 않은 파일을 생성하지 않는 연결, 실제 PNG·영상 다운로드·복사·재생, 빈/긴 입력과 실패·재시도 검사도 유지한다. 유료 API 호출은 없다. 현재 앱의 AI·인증·클라우드 보관·공유 API는 미연결 체험형이다.

## 범위와 근거

스크롤을 막거나 전체 화면을 transform으로 축소하지 않는다. 긴 소개·홍보 문구, 많은 저장 결과, 펼친 안내, 글자 확대·가상 키보드처럼 물리적으로 한 화면에 담기 어려운 경우에는 필요한 만큼 자연스럽게 스크롤할 수 있다. 실물 휴대전화·Safari/VoiceOver를 검증했다고 주장하지 않는다.

[검증 화면](../docs/review/evidence-20261014-screen-fit/README.md)을 참조한다. 상세 측정은 작업 공간의 `output/final-integration-review/screen-fit/` 및 `home-fit-agent/after-final/`에 기록했다. 검증 화면은 문서 폴더에만 두며 실행 앱의 public 자산에는 넣지 않는다. 최종 게시·병합·배포 상태는 GitHub PR과 사용자 보고에서 확인한다.
